# Contributing

## Development setup

Requires Python 3.11+, [uv](https://docs.astral.sh/uv/) and, for scraping, Google Chrome.
From the repository root (Windows PowerShell or a Unix shell):

```bash
uv sync --locked           # editable install + dev tools + the `scrape` and `analysis` extras
uv run pre-commit install  # git hooks
uv sync --extra sentiment  # optional: transformer models (PyTorch)
uv sync --group notebooks  # optional: JupyterLab and notebook tools
```

With `make` installed, `make help` lists every shortcut (`make install`, `make check`, ...).
`pyproject.toml` holds the dependencies and all tool configuration; `uv.lock` pins the
resolved versions.

## Repository layout

```
configs/games.toml          this project's game registry (app id + name)
configs/presets.toml        this project's analysis presets
data/raw/, data/processed/  scraped and cleaned data (gitignored)
docs/                       user guides; the API reference is generated by pdoc
notebooks/                  exploratory analysis of the project datasets
src/steam_review_analysis/
    scraping/               settings, browser, parsers, collector, `scrape_games` workflow
    processing/             pandas only: raw -> typed, deduplicated data
    analysis/               preprocessing, VADER and transformer sentiment, statistics, plots
    config.py  schema.py    data-directory resolution, game registry, column names, `Review`
    io.py                   reading and (atomically) writing the CSVs
    cli.py                  `steam-review-analysis` command
tests/
```

Data flows one way: `scraping` writes raw CSVs, `processing` turns them into the processed
dataset, and `analysis` reads that. `scraping` and `processing` never import each other; both
depend only on `schema`, `config` and `io`.

### Packaging rules

- **Core stays light.** The package must import with only pandas installed. Modules that need
  an extra (`selenium`, `nltk`, `scipy`, `matplotlib`, ...) live in `scraping/` or
  `analysis/`, and the CLI imports them only inside the command that runs. CI installs the
  wheel without extras and fails if an optional dependency leaks into the core.
- **No repository paths.** Never locate files relative to `__file__`. Data locations come from
  `steam_review_analysis.config`; project configuration lives in `configs/`, which is not
  shipped.
- **No surprise side effects.** Library code does not configure logging, print, or download
  anything; only the CLI does.
- **Write atomically.** Write output through `io.atomic_path` so interrupted runs never leave
  half-written files.
- **Honest lower bounds.** CI tests the oldest dependency versions allowed in
  `pyproject.toml`. Raise a bound when you use a newer feature.

## Quality checks

```bash
make check    # ruff lint + format check, mypy --strict, pytest with coverage
make format   # auto-fix lint and formatting
```

Without `make`: `uv run ruff check .`, `uv run ruff format --check .`, `uv run mypy`,
`uv run pytest`. Tests use simulated browsers and temporary directories; they never contact
Steam or touch the repository's data.

Pre-commit runs Ruff, mypy, file-hygiene checks and `uv lock` on commit, and pytest on push.
CI (`.github/workflows/ci.yml`) runs on pull requests and pushes to `main`:

- lint, types and tests on Python 3.11, 3.12, 3.13 and 3.14 with the locked versions;
- tests with the lowest allowed dependency versions;
- building the wheel and sdist, `twine check`, and a smoke test of the wheel installed without
  extras, outside the repository.

### Docstrings

Every public module, class, function and method needs a Google-style docstring; Ruff's `D`
rules enforce it. The API reference is generated from them:

```bash
make docs         # live preview
make docs-build   # static HTML in artifacts/docs/
```

The `Docs` workflow publishes the reference to GitHub Pages on every push to `main`
(one-time setup: repository Settings → Pages → Source: *GitHub Actions*).

Tests have docstrings describing the scenario. Fixtures and helpers document their arguments
and return values; ordinary tests need not repeat fixture arguments in an `Args` section.

## Releasing

Versions follow [Semantic Versioning](https://semver.org); `version` in `pyproject.toml` is the
single source (`steam_review_analysis.__version__` reads the installed metadata).

1. Move the `Unreleased` entries in `CHANGELOG.md` under the new version and date.
2. Bump the version: `uv version --bump patch` (or `minor` / `major`), then `uv lock`.
3. Commit, then tag and push: `git tag v0.2.0 && git push origin main v0.2.0`.

Pushing the tag runs `.github/workflows/release.yml`: it checks that the tag matches the
version, runs the tests, builds and checks the distributions, publishes them to PyPI and
creates a GitHub release.
